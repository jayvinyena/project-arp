## 무엇을 쟀나

| 항목 | 뜻 |
|---|---|
| 첫 화면 | 페이지를 연 순간부터 첫 데이터(현실 규모)의 계산 결과가 화면에 나오기까지. HTML·JS 받기, SQLite 준비, 파일 받기·열기, 검증, 읽기, 엔진, 그리기를 모두 포함 |
| 열기→화면 | 파일 받기 시작부터 그 파일의 결과가 화면에 나오기까지 |
| 재계산 | 값 하나(첫 파트 첫 달 인원 ±1)를 고친 뒤 검증 + 바뀐 표 다시 읽기 + 엔진. 15회 |
| 저장 내보내기 | 메모리 DB를 파일 바이트로 만드는 시간. 디스크 쓰기는 브라우저 파일 API가 따로 한다 |

CPU는 이 PC 그대로(보통)와, 느린 노트북을 흉내 낸 4배 느리게(크롬 CPU 제한) 두 조건으로 쟀다. 처음 열기는 브라우저 캐시를 끈 상태다.

## 측정하며 바꾼 것

- **처음:** 재계산마다 표 전체를 다시 읽었다. 현실 규모에서 재계산이 26ms, 느린 CPU에서 115ms로 목표를 넘었다.
  - 브라우저에서 시간이 가장 많이 든 곳은 "SQLite 행을 JS 객체로 바꾸기"였다. 현실 규모 전체 읽기에 18ms, 느린 CPU에서 83ms가 들었다.
- **바꾼 것:** [`ProjectSession`](../core/pipeline.ts)을 만들었다.
  - 엔진 입력을 메모리에 두고, 고친 표만 다시 읽는다.
  - 시나리오는 그 시나리오가 건드리는 표만 SAVEPOINT 안에서 읽어 덮어 쓴다.
  - 결과: 재계산 26 → 10ms, 느린 CPU 115 → 45ms.
  - 매번 전부 읽는 계산과 결과가 같은지 검사한다(`test/engine.test.mjs` 작업 세션).

## 2단계로 넘기는 것

- 엔진을 **Web Worker**로 옮긴다. 지금은 메인 스레드에서 돈다. 느린 CPU에서 과부하 규모를 계산하는 0.1초 남짓 동안 화면이 멈추지 않게 하기 위해서다.
- 검증 36개는 매번 전부 돈다(현실 규모 5–25ms). 더 줄일 필요가 생기면, 고친 표와 관련된 규칙만 돌리도록 규칙에 "쓰는 표" 정보를 붙인다.
- 실제 파일 저장(File System Access API) 시간은 앱 화면에서 잰다.
