# 데이터 모델 v1

정의는 [`schema/schema-v1.sql`](../schema/schema-v1.sql)이 원본이다. 이 문서는 왜 그렇게 나눴는지와 계산에서 어떻게 쓰이는지를 설명한다.
용어는 [용어 사전](00-glossary.md)을 따른다.

## 1. 설계 원칙

1. **파일 하나 = 프로젝트 하나.** 파트, 리소스 종류, 업데이트 유형, 공정, 근무 달력은 모두 파일 안의 데이터다. 코드에 고정된 이름이 없어서 어떤 게임에도 쓸 수 있다.
2. **같은 값은 한 곳에만.** 예를 들어 근무일 수는 저장하지 않고 근무 달력에서 계산한다. 동기화할 사본이 없다.
3. **표 제약은 형식만, 값 규칙은 검증으로.** 표는 형(숫자·글자), 날짜 모양, 키와 참조만 막는다. `최저 ≤ 목표 ≤ 확장` 같은 규칙은 [검증 규칙](03-validation-rules.md)이 확인한다. 그래서 가져오기와 작업 중 저장은 막히지 않고, 문제는 "계산 불가 + 이유"로 보인다.
4. **조용한 기본값 없음.** 비어 있으면 NULL이고, 계산에 필요한데 비어 있으면 검증 오류다. 0·1처럼 뜻이 분명한 값만 기본값을 둔다.
5. **원본과 시나리오 분리.** 시나리오는 원본을 바꾸지 않는 변경 목록이다. 반영할 때만 원본이 바뀌고 변경 이력이 남는다.

## 2. 표 한눈에 보기

```
settings ─ holidays                         (프로젝트 설정, 근무 달력)

parts ─┬─ part_overlaps                     (공정 순서, 파트 쌍 겹침률)
       └─ capacity                          (파트 × 월 인력)

resource_groups ─ resource_types ─ resource_parts ─ efforts ─ effort_profiles ─ effort_mix
                                   (거치는 파트·재작업률)  (프로필별 공수)            (파트별 섞는 비율)

update_types ─ type_templates               (유형별 기본 물량)
     └─ updates ─┬─ volumes                 (업데이트 × 리소스 종류 물량)
                 └─ progress                (업데이트 × 리소스 종류 × 파트 완료 수량)

scenarios ─ scenario_changes                (원본 위 변경 목록)
change_log, meta                            (변경 이력, 파일 정보)
```

## 3. 표별 설명

### 설정 · 근무 달력
| 표 | 한 줄 | 핵심 항목 |
|---|---|---|
| `settings` | 프로젝트에 하나 | 계획 기간(시작 월·끝 월), 근무 요일(`1111100` = 월–금), 여유율, 기본 겹침률, 부하율 기준 3단계, 늦음 기준(영업일), 기본 물량 구간 |
| `holidays` | 휴일 하루 | 날짜, 이름. 근무 요일에 걸친 날만 근무일에서 뺀다 |

### 파트 · 공정
| 표 | 한 줄 | 핵심 항목 |
|---|---|---|
| `parts` | 파트 하나 | `sort_order` = 공정 순서, 사용 여부 |
| `part_overlaps` | 이어지는 두 파트 | 겹침률. 없는 쌍은 `settings.default_overlap_rate` |

공정 순서는 파트 순서 하나로 정한다. 리소스 종류는 `resource_parts`에 있는 파트만 거치고, 건너뛴 파트가 있으면 실제로 이어지는 두 파트의 겹침률을 쓴다.

### 리소스 · 공수
| 표 | 한 줄 | 핵심 항목 |
|---|---|---|
| `resource_groups` | 분류 하나 | 표시·합계용 |
| `resource_types` | 리소스 종류 하나 | 분류, 순서, 사용 여부 |
| `resource_parts` | 리소스 종류가 거치는 파트 하나 | 재작업률 |
| `effort_profiles` | 공수 판 하나 | `BASE`(기본)는 필수. 예: `AI`(AI 사용 시) |
| `efforts` | 리소스 × 파트 × 프로필 | 1개당 인·일 |
| `effort_mix` | 파트 × 프로필 | 섞는 비율. 파트별 합 1. 행이 없는 파트는 `BASE` 100% |

공수를 프로필별 행으로 둔 이유: "AI 사용 시", "숙련자", "외주 기준" 같은 판을 표 구조를 바꾸지 않고 더할 수 있다.

계산에 쓰는 공수 = Σ (비율 × 그 프로필 공수). 어떤 리소스에 그 프로필 값이 없으면 그 몫은 `BASE` 값을 쓰고, 결과 근거에 적는다. 이것은 숨은 기본값이 아니라 프로필의 정의다.

### 업데이트 · 물량 · 실적
| 표 | 한 줄 | 핵심 항목 |
|---|---|---|
| `update_types` | 유형 하나 | `is_launch`: 런칭 유형 |
| `type_templates` | 유형 × 리소스 종류 | 기본 최저·목표·확장. 새 업데이트를 만들 때 복사만 한다 |
| `updates` | 업데이트 하나 | 유형, 시작일, 제작 완료 목표일, 출시일, 숫자 우선순위, 상태 |
| `volumes` | 업데이트 × 리소스 종류 | 최저·목표·확장, 필수 여부, 업데이트 안 순위, 난이도, 재사용률, 외주 수량 |
| `progress` | 업데이트 × 리소스 종류 × 파트 | 완료 수량, 기준일, 실투입 인·일(`spent_days`, v3) |

런칭은 별도 표가 아니라 `is_launch` 유형의 업데이트다. 그래서 런칭 물량 설계와 업데이트 계획이 같은 엔진, 같은 인력을 쓴다. 런칭 물량 설계 화면은 런칭 업데이트 하나에 집중한 화면일 뿐이다.

### 인력
| 표 | 한 줄 | 핵심 항목 |
|---|---|---|
| `capacity` | 파트 × 월 | 인원, 가동률, 생산성, 외주 인력(인·일), 지원 인력(인·일) |

외주는 두 가지로 나눈다.
- **수량 외주** (`volumes.outsource_qty`): 결과물을 통째로 맡긴다. 내부 공수가 들지 않는다.
- **인력 외주** (`capacity.outsource_days`): 외부 인력이 우리 공정 안에서 일한다. 작업 가능량에 더한다.

계획 기간의 모든 달에 `capacity` 행이 있어야 한다. 마지막 달 값으로 뒤를 채우는 일은 앱의 "채우기" 기능이 사람의 확인을 받고 실제 행으로 만든다.

### 시나리오
| 표 | 한 줄 | 핵심 항목 |
|---|---|---|
| `scenarios` | 시나리오 하나 | 이름, 만들 때의 원본 데이터 버전, 원본에 반영한 시각(`applied_at`, v2) |
| `scenario_changes` | 변경 하나 | `SET`(값 바꾸기), `INSERT`(행 추가: 예를 들어 가상의 업데이트), `DELETE`(행 빼기). 동작 번호·이름(`group_no`·`label`, v2) |

대상은 계산에 쓰는 표(`settings`, `part_overlaps`, `resource_parts`, `efforts`, `effort_mix`, `updates`, `volumes`, `capacity`)로 한정한다. 키는 기본 키를 `|`로 이은 글자다. 예: `LAUNCH|CHAR_NEW`, `MODELING|2027-03`.

시나리오에 쓸 수 있는 변수:

| 바꾸고 싶은 것 | 변경 |
|---|---|
| 파트 인원, 채용 시점 | `capacity` SET headcount (월별) |
| 외주 인력 | `capacity` SET outsource_days |
| AI 사용 | `effort_mix` SET share (예: 원화 AI 0.5 → 0.8) |
| 물량 | `volumes` SET min/target/stretch, outsource_qty |
| 출시일, 우선순위 | `updates` SET release_date, priority |
| 업데이트 추가·제외 | `updates`·`volumes` INSERT / DELETE |
| 공정 겹침 | `part_overlaps` SET overlap_rate |

### 이력 · 파일 정보
| 표 | 한 줄 | 핵심 항목 |
|---|---|---|
| `change_log` | 항목 하나의 변경 | 묶음 번호, 시각, 편집자, 대상·키·항목, 이전·이후 값(JSON), 이유 |
| `meta` | 키-값 | `project_name`, `created_at`, `data_version`, `lock_holder`, `lock_heartbeat_at`, `saved_by_app` |

## 4. 계산에서 쓰는 식

```
필요 공수(스테이지) = 남은 수량 × 공수(섞은 값) × 난이도 × (1 − 재사용률) × (1 + 재작업률) × (1 + 여유율)
남은 수량          = max(0, 물량(구간) − 외주 수량 − 완료 수량(그 파트))
작업 가능량(파트·월) = 인원 × 근무일 수 × 가동률 × 생산성 + 외주 인력 + 지원 인력
근무일 수(월)      = 근무 요일에 해당하는 날 수 − 그중 휴일 수
```

배정 순서(1단계 엔진의 약속): 업데이트 우선순위 → 출시일 → 필수 여부 → 업데이트 안 순위 → 리소스 종류 순서.

## 5. 규모 예상

| 항목 | 기준 규모 |
|---|---|
| 파트 | 4–10 |
| 리소스 종류 | 500 |
| 업데이트 | 50 |
| 물량 행 | 최대 25,000 (실제로는 업데이트마다 일부만) |
| 인력 행 | 파트 10 × 36개월 = 360 |

이 규모의 파일 크기와 읽기 시간은 `tools/gen-scale.mjs`로 잰다.

## 6. 지금 도구에서 바꾼 점 (참고)

| 지금 | 새 모델 | 이유 |
|---|---|---|
| 우선순위 HIGH/MEDIUM/LOW | 숫자 순위 | 같은 등급 안의 순서가 모호했다 |
| 추가·취소·이월 수량 항목 | 없음. 물량을 고치고 이력에 이유 | 같은 물량을 여러 칸이 나눠 가졌다 |
| 월 근무일 수 입력 | 근무 달력에서 계산 | 입력 실수, 휴일 미반영 |
| 계획 기간 뒤 인력 자동 연장 | 모든 달에 행 필수 | 조용한 가정이 결과를 바꿨다 |
| 기본·AI 공수 두 칸 | 공수 프로필 행 | 판을 더할 때 구조가 바뀌지 않게 |
| 리소스 계층(GROUP/ITEM, 부모 ID) | 분류 + 종류 두 단계 | 계산은 종류 단위만 쓴다 |
| 파이프라인 템플릿(인계 방식, 묶음, 대기일) | 파트 순서 + 겹침률 | 하나의 규칙으로 |
| 시나리오 공개 범위, 잠금, 소유자 | 없음 | 소수 관리자가 파일로 공유 |
