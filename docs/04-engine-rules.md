# 계산 엔진 규칙 v1

구현: [`engine/`](../engine/) (TypeScript, 의존 패키지 없음). 입구는 `runPlan(데이터, { planMode })`.
계산 흐름(파일 → 시나리오 얹기 → 검증 → 읽기 → 엔진): [`tools/lib/pipeline.mjs`](../tools/lib/pipeline.mjs).

## 1. 입력과 전제

- 입력은 프로젝트 파일의 표를 그대로 읽은 것이다([데이터 모델](01-data-model.md)).
- [검증 규칙](03-validation-rules.md)에 오류가 하나라도 있으면 엔진을 돌리지 않는다. 엔진이 받는 데이터는 오류가 없다고 본다. 그래도 필요한 값이 없으면 숫자를 지어내지 않고 `EngineInputError`로 멈춘다.
- 계산 대상은 상태가 계획·진행인 업데이트뿐이다.
- 시나리오는 엔진 밖에서 원본에 잠시 얹는다(SAVEPOINT 후 되돌림). 엔진은 시나리오를 모른다.

## 2. 시간

- 단위는 **영업일**이다. 근무 달력(근무 요일 − 공휴일·회사 휴무일)으로 계획 기간의 영업일 목록을 만든다.
- 하루 작업 가능량 = 그 달 작업 가능량 ÷ 그 달 영업일 수. 그래서 월 합계가 인력 표의 월 작업 가능량과 정확히 같다.
- 월 작업 가능량 = 인원 × 영업일 수 × 가동률 × 생산성 + 외주 인력 + 지원 인력.

## 3. 스테이지

- 작업 단위는 `업데이트 × 리소스 종류 × 파트`다. 리소스 종류가 거치는 파트(`resource_parts`)만 만들고, 파트 순서대로 잇는다.
- 필요 공수 = 남은 수량 × 공수(프로필 섞은 값) × 난이도 × (1 − 재사용률) × (1 + 재작업률) × (1 + 여유율).
- 남은 수량 = 물량(구간) − 외주 수량 − 그 파트 완료 수량, 0 미만이면 0.
- 필요 공수가 0인 스테이지는 계획 기간 전에 이미 끝난 것으로 본다.

## 4. 겹침률

겹침률이 r이면 **앞 스테이지가 (1 − r)만큼 진행된 다음 날 아침**부터 다음 스테이지를 시작할 수 있다.

- 판정은 그날 아침 진행률로 한다. 같은 날 안에서 앞 공정이 조건을 채우고 바로 다음 공정이 시작되는 연쇄는 없다.
- 앞 공정이 어제까지 시작하지 않았으면 다음 공정도 시작하지 않는다(r = 1이어도 하루는 뒤).
- 건너뛴 파트가 있으면 실제로 이어지는 두 파트의 겹침률을 쓴다. 그 쌍이 없으면 기본 겹침률.
- **완료 제약:** 다음 스테이지는 앞 스테이지보다 먼저 끝나지 않는다. 일을 먼저 마쳐도 완료일은 앞 스테이지의 완료일이다.

예시(검사로 고정): 원화 10영업일, 모델링 15영업일, 인원 경합 없음.

| 겹침률 | 모델링 시작 | 모델링 완료 |
|---|---|---|
| 20% | 9일째 | 23일째 |
| 0% | 11일째 | 25일째 |

## 5. 하루의 순서

1. 오늘 시작일이 된 업데이트의 스테이지를 들인다. 앞 공정이 없거나 이미 끝났으면 바로 "준비됨"이다.
2. 어제 일을 받은 스테이지의 다음 스테이지가 오늘 아침 조건을 채우면 "준비됨"이 된다. 준비 여부는 앞 공정이 진행될 때만 바뀌므로 그 스테이지만 확인한다(속도).
3. 파트마다 준비된 스테이지를 **배정 순서**대로 하루 작업 가능량만큼 채운다. 한 스테이지가 하루에 받을 수 있는 양에 상한은 없다.
4. 모든 스테이지가 끝나거나 계획 기간이 끝나면 멈춘다. 남은 스테이지는 "기간 안에 못 끝냄"이다.

**배정 순서:** 업데이트 우선순위 → 출시일(없으면 뒤) → 업데이트 표시 순서 → 필수 먼저 → 업데이트 안 순위 → 리소스 종류 순서.

## 6. 결과

| 결과 | 내용 |
|---|---|
| 업데이트 | 완료 예정일(모든 스테이지 완료일 중 가장 늦은 날), 판정, 늦은 영업일, 심각 여부, 근거 |
| 파트 | 계획 기간 필요 공수 합계, 작업 가능량 합계, 부하율과 판정(여유·주의·초과·심각), 가장 밀린 달 |
| 파트 × 월 | 영업일, 작업 가능량, 배정량, 가동 비율, 달 끝에 남은 일 |
| 스테이지 | 준비일, 시작일, 작업 종료일, 완료일, 인력 대기 영업일, 겹침률과 출처 |
| 날짜별 | 파트별 하루 작업 가능량과 배정량(차트·검사용) |

**판정:**

| 판정 | 조건 |
|---|---|
| 목표 안 | 완료 예정일 ≤ 제작 완료 목표일(없으면 출시일) |
| 빠듯 | 완료 예정일 ≤ 출시일 |
| 늦음 | 출시일 뒤. 늦은 영업일 수를 함께 준다 |
| 심각 | 늦음이 `late_warn_workdays`를 넘거나, 기간 안에 못 끝냄 |
| 출시일 없음 | 완료 예정일만 보여주고 판단하지 않는다 |

**근거:** 가장 늦게 끝나는 스테이지(못 끝냈으면 가장 많이 남은 스테이지)의 파트, 리소스 종류, 인력 대기 영업일, 작업 영업일, 남은 일. 예: "모델링 · 프랍 · 남은 일 392.7인·일".

## 7. 검사 (test/engine.test.mjs)

- 손 계산 예시 3개 (겹침 20%, 0%, 100%와 완료 제약)
- 성질 검사 (정상·과부하 샘플 × 물량 구간 3개, 현실 규모)
  - 어느 날도 파트 배정량이 하루 작업 가능량을 넘지 않는다
  - 배정 합 = 끝낸 일 합
  - 업데이트 시작일 전에는 배정하지 않는다
  - 다음 스테이지는 앞 스테이지가 시작한 다음 날 이후, (1 − r) 진행 뒤에만 시작한다
  - 다음 스테이지는 앞 스테이지보다 먼저 끝나지 않는다
- 단조성 (정상 샘플 런칭): 겹침률 ↑ → 늦어지지 않음, 인원 ↑ → 늦어지지 않음, 최저 ≤ 목표 ≤ 확장
- 판정·근거, 출시일 없음, 오류 파일 계산 거부, 시나리오(결과 변화, 원본 그대로)
- 골든 결과: 정상 샘플 목표안 (`test/golden/normal-target.json`, 바꿀 때는 `UPDATE_GOLDEN=1 npm test` 후 차이를 확인)
- 속도: 현실 규모 한 번 계산 100ms 이내

**한계:** 여러 업데이트가 인력을 나눠 쓰는 우선순위 배정은, 드물게 한 곳을 좋게 해도 다른 업데이트가 늦어질 수 있다(배정 순서가 바뀌는 효과). 단조성 검사는 가장 우선인 런칭에 대해서만 한다.
