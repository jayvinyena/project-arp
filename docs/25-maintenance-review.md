## 2. 위험이 큰 것

### 2.1 타입 검사가 없다 (가장 중요)

코드는 TypeScript(.ts · .tsx)인데 **타입 검사기가 설치되어 있지 않다**. Node와 Vite는 타입을 지우고 실행만 하므로, 칸 이름을 잘못 적거나 화면과 계산 스레드의 모양이 어긋나도 실행해 보기 전에는 모른다.

임시로 엄격 모드(strict) 검사를 돌려 보니 **오류 5개뿐**이다(2026-11-10). 지금 넣으면 비용이 거의 없다.

| 위치 | 내용 |
|---|---|
| core/edits.ts:117 | 함수 끝에 돌려주는 값이 없는 경로 |
| core/pipeline.ts:5 · 227 | 규칙 파일(.mjs)에 형식 정보가 없어 `any` |
| web/app/ui/AssetsPage.tsx:44 | 썸네일 바이트를 Blob으로 만들 때 형식 불일치(동작은 함) |

### 2.2 새 표를 더할 때 손으로 고칠 곳이 흩어져 있다

이번 세션에서 표를 3번(asset_attrs · people 등) 더하면서 매번 아래를 따로 고쳤다. 하나라도 빠지면 되돌리기 · 예시 파일 · 옛 파일 시험이 조용히 틀린다.

| 고칠 곳 | 하는 일 |
|---|---|
| core/migrate.ts | 표 만들기(단계) |
| core/history.ts `KEYS` · `TARGET_NAME` · `FIELD_NAME` · `CHILD_TABLES` | 이력 · 되돌리기 |
| tools/lib/project-db.mjs `TABLE_ORDER` | 예시 파일 만들기 순서 |
| tools/build-samples.mjs | 옛 구조(v1) 시험 파일에서 지울 표 |
| test/assets.test.mjs · phase0.test.mjs | 구조 버전 숫자 |

### 2.3 화면 ↔ 계산 스레드 약속이 글자로만 이어져 있다

화면(rpc.ts)은 `call('assets', …)`처럼 **이름 글자**로 요청하고, 돌려받는 모양도 rpc.ts에 따로 적는다. 계산 스레드(worker.ts)의 받는 쪽은 `payload: any`다. 한쪽 이름이나 모양을 바꿔도 다른 쪽은 모른다(타입 검사가 생겨도 이 부분은 잡지 못한다).

### 2.4 배포 · 저장소 흐름이 길고 손이 많다

- arp-next가 **옛 도구(Apps Script)와 같은 부모 저장소 안**에 있고, GitHub에는 `subtree split`으로 떼어 올린다. 부모 저장소에는 지운 파일 · 수십 개의 임시 폴더가 섞여 있어 실수하기 쉽다.
- GitHub 올리기는 release.ps1 밖의 손 작업이다(그때마다 private 0개 확인).
- 줄 끝 문자(LF/CRLF) 정책이 없어 커밋마다 경고가 나고, 일괄 수정 때 내용 변화 없는 파일이 바뀐 것처럼 잡힌다.
- 검사는 이 PC에서만 돈다(자동 검사 없음).

## 4. 제안

### 1순위 — 작고 효과 큼(반나절 안팎)

| 제안 | 방법 | 확인 |
|---|---|---|
| **A. 타입 검사 넣기** | 개발 패키지 `typescript` 추가, `tsconfig.json`, `npm run check`(형식 검사). 오류 5개 고치기. `npm test` · release.ps1 앞에 `check` | 일부러 칸 이름을 틀리면 check가 실패 |

## 5. 하지 않기를 권하는 것

- **큰 틀 바꾸기**(다른 화면 라이브러리 · 상태 관리 도구 · 서버 도입): 지금 구조(로컬 우선 · 파일 하나 · 작은 의존)가 유지비 0 원칙과 맞고, 문제는 구조가 아니라 **검사 장치와 파일 크기**다.
- **한 번에 다 나누기**: F · G · H는 기능 작업과 섞이면 되돌리기 어렵다. 화면 하나씩, "옮기기만 하는 커밋"으로 나눈다.
