# 배치별 완료 예측 설계

2026-11-11 · 상태: **적용함**(8절 추천안대로, 6번은 설명 줄로) — 결과는 9절. [docs/20](20-asset-management.md) 12절 "2단계: 배치 예측"을 구체화한다.

요청: docs/32 추천 순서 6번 "에셋 2단계: 배치별 완료 예측" — 설계 문서 먼저.

## 1. 지금

| 곳 | 지금 |
|---|---|
| 배치 | 업데이트 안의 납품 묶음. 이름 · 마감일 · 순서(끌어서 바꿈). 에셋이 배치에 속한다(없으면 미배정) |
| 에셋 → 계산 | 에셋의 파트별 완료 · 해당 없음 수가 작업 진척(완료 수량 · 기준일)으로 자동 집계된다. **엔진은 배치를 모른다** |
| 엔진 | 스테이지 = 업데이트 × 리소스 × 파트(수량). 파트마다 준비된 스테이지를 순서대로 채운다. 순서 = 업데이트 우선순위 → 출시일 → 업데이트 순서 → 필수 먼저 → 업데이트 안 순위 → 리소스 순서 |
| 화면 | 현황판 배치 카드: 마감 · D-day · 완료 에셋 · 진행(끝난 파트 비율). "배치별 완료 예측은 2단계" |

빠진 것: **"1차 납품이 마감에 맞나?"** 를 알 수 없다. 업데이트 완료 예정만 있다.

|---|---|
| Jira Plans(Advanced Roadmaps) | 이슈를 **순위대로** 팀 인력(스프린트 용량)에 채워 일정을 잡고, 그 결과로 릴리스 예상 날짜 · 용량 초과를 보인다 — [How does the auto-scheduler work](https://support.atlassian.com/jira-software-cloud/docs/how-does-the-auto-scheduler-in-advanced-roadmaps-work), [Scheduling behavior](https://confluence.atlassian.com/spaces/JIRAPortfolioServer0325/pages/1004932455/Scheduling+behavior) |

ARP의 엔진은 Jira Plans와 같은 계열(순서대로 인력을 채워 배정)이다. 그래서 **배치 순서를 배정 순서에 넣는 것**이 자연스럽다.

## 3. 방식

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 계산 뒤 나누기 | 엔진은 그대로. 스테이지가 날마다 한 일을 그 스테이지 에셋에 배치 순서대로 나눠 담아, 에셋 · 배치가 언제 끝나는지 센다 | 엔진 배정이 그대로라 지금 결과 · 옛 도구 비교가 모두 같다 | 엔진은 리소스 순서로 일한다. 같은 파트에서 리소스 X의 2차 배치가 리소스 Y의 1차 배치보다 먼저 배정돼, **1차 배치가 2차보다 늦게 끝나는 예측**이 나온다(4절). 실제로는 1차부터 하므로 현실과 어긋난다 |
| **B. 배치를 배정 순서에 넣기(추천)** | 에셋이 있는 업데이트 × 리소스 스테이지를 **배치마다 나눈다**(수량 = 그 배치의 남은 에셋). 배정 순서에 배치 순서를 넣어 업데이트 안에서는 1차 배치(모든 리소스) → 2차 배치 순서로 일한다. 공정 연결(파이프라인 · 겹침률 · 병렬)은 배치마다 따로 | "배치 순서대로 납품한다"는 실제 일하는 방식과 같다. 배치 완료일이 스테이지 완료일에서 바로 나온다 | **배치가 있는 업데이트는 완료 예정이 바뀐다**(대개 빨라지거나 순서가 달라짐). 엔진 · 스테이지 수가 늘어난다(배치 수만큼) |
| C. B + 끄기 설정 | B에 "배치 순서로 계산" 설정(끄면 A처럼 리소스 순서) | 예전 결과와 비교 가능 | 설정 하나 더, 두 가지 결과를 설명해야 함 |

## 4. 손 계산 예시 (B를 고르는 까닭)

원화 1명 · 모델링 1명, 원화 2일/개 · 모델링 3일/개, 겹침 0%. 한 업데이트에 리소스 X(1차 2개 · 2차 2개), 리소스 Y(1차 2개). 리소스 순서 X → Y.

| | A(지금 배정 + 나누기) | B(배치 순서로 배정) |
|---|---|---|
| 원화 순서 | X 4개(1 ~ 8일) → Y 2개(9 ~ 12일) | X 1차(1 ~ 4일) → Y 1차(5 ~ 8일) → X 2차(9 ~ 12일) |
| 모델링 순서 | X(9 ~ 20일, 원화 X 전체를 기다림) → Y(21 ~ 26일) | X 1차(5 ~ 10일) → Y 1차(11 ~ 16일) → X 2차(17 ~ 22일) |
| **1차 배치 완료** | **26일**(Y 1차가 맨 뒤) | **16일** |
| 2차 배치 완료 | 20일 — 1차보다 먼저 끝남 | 22일 |
| 업데이트 완료 | 26일 | 22일 |

A는 1차 배치를 "26일"로 예측해 실제(1차부터 작업)와 크게 다르다. B는 일하는 순서대로 예측한다. 이 예시를 단위 시험으로 고정한다.

## 5. B 설계

### 5.1 배정 순서

```
업데이트 우선순위 → 출시일 → 업데이트 순서 → [배치 순서] → 필수 먼저 → 업데이트 안 순위 → 리소스 순서
```

- 배치 순서 = 배치 표 순서(끌어서 바꿈). 마감일이 아니라 순서를 쓴다(마감이 같거나 비어도 순서는 정해져 있고, 사람이 정한 순서가 우선).
- **배치 밖 일**(미배정 에셋 · 아직 에셋이 없는 물량 · 에셋을 쓰지 않는 리소스)은 그 업데이트의 **배치들 뒤**(정할 것 2).

### 5.2 수량 나누기

엔진의 남은 일 총량은 지금과 같게 둔다(물량 기준: 물량 − 외주 − 완료). 이것을 배치 순서대로 나눠 담는다.

| 순서 | 담는 수량(파트마다) |
|---|---|
| 1차 · 2차 … 배치 | 그 배치 에셋 중 이 파트가 아직 끝나지 않은 수(완료 · 해당 없음 제외). 계획 템플릿(최소안 · 기본안 · 최대안)에 들어가는 에셋만 |
| 배치 밖 | 남은 총량 − 배치에 담은 수(미배정 에셋 + 아직 에셋이 없는 물량) |
| 넘침 | 배치 에셋이 남은 총량보다 많으면 뒤 배치부터 모자란다 → 그 배치는 **"물량 밖 n개"**(물량을 늘리거나 에셋을 줄이라는 알림, 완료 예정은 "물량 안 몫"까지만) |

- 파트 총 공수 · 필요 공수 표는 지금과 같다(총량이 같으므로). 바뀌는 것은 순서와 날짜뿐.
- 이미 끝낸 몫(작업 진척 · 앞 공정 진행률)은 배치마다 그 배치 에셋 기준으로 센다.

### 5.3 공정 연결

배치마다 따로 이어진다: X 1차의 모델링은 X 1차의 원화를 기다린다(X 2차 원화는 기다리지 않는다). 파이프라인 단계 순서 · 겹침률 · 병렬 묶음(docs/28 · 30)은 그대로 배치마다 적용한다.

### 5.4 결과 · 판정

| 값 | 뜻 |
|---|---|
| 배치 완료 예정 | 그 배치 모든 스테이지(리소스 × 파트)의 완료일 중 가장 늦은 날 = 마지막 파트까지 끝나는 날(docs/20 11절 6번 "모든 파트 완료" 기준) |
| 판정 | **마감 안** · **빠듯**(마감 전 N영업일 안, N = 설정의 "늦음 경고 영업일") · **늦음**(+n영업일) · **못 끝냄**(계획 기간 안) · **마감 없음** · **물량 밖**(5.2 넘침) |
| 늦어진 까닭 | 업데이트 판정과 같은 방식: 가장 오래 인력을 기다린 파트 · 리소스 |

### 5.5 보여 줄 곳

| 화면 | 더하는 것 |
|---|---|
| 업데이트 계획(목록 · 상세) | 업데이트 아래 배치 줄: 마감 · 완료 예정 · 판정 · 차이(영업일) |
| 에셋 › 배치 탭 | 배치 표에 완료 예정 · 판정 칸 |
| 제작 현황판 배치 카드 | 진행 옆에 완료 예정 · 판정(늦음이면 까닭 한 줄) |
| 보고용 엑셀 | 배치 시트(업데이트 · 배치 · 마감 · 완료 예정 · 판정) |
| 데이터 점검 | 새 주의: 배치 마감이 업데이트 출시일보다 뒤, 배치 에셋이 물량보다 많음(물량 밖) |

시뮬레이션 비교표의 배치 열 · 배치를 시나리오 대상에 넣기는 나중(docs/20 3단계).

### 5.6 엔진 입력

엔진은 지금처럼 순수 계산으로 둔다. core가 에셋 표에서 **배치 작업량**을 만들어 넘긴다.

```
batch_work(update_id, resource_type_id, part_id, batch_id, rank, remaining_qty, done_qty)
```

- 에셋 상태 · 배치 순서가 바뀌면 다시 만든다(계산 캐시 무효화에 에셋 · 배치 표를 더한다).
- 에셋이 없는 파일 · 업데이트는 batch_work가 비어 **결과가 바이트까지 지금과 같다**(골든 · 옛 도구 비교 그대로).
- 스테이지 수: 배치 수만큼 늘어난다(운영 규모 23종 × 4파트 × 3업데이트 × 배치 3 ≈ 800). 시나리오 3개 비교 속도를 함께 잰다(목표 0.3초).

## 6. 시험 계획

| 종류 | 내용 |
|---|---|
| 손 계산 | 4절 예시(1차 16일 · 2차 22일 · 업데이트 22일), 겹침 20%, 병렬 묶음과 배치 함께, 물량 밖 |
| 같음 | 배치 없는 예시 · 운영 시트: 결과 완전히 같음(골든 · 옛 도구 비교) |
| 성질 | 배치 순서를 바꾸면 앞으로 간 배치는 늦어지지 않는다 · 인원을 늘리면 늦어지지 않는다 |
| 크롬 | 업데이트 계획 배치 줄 · 에셋 배치 표 · 현황판 카드에 예정 · 판정, 배치 순서를 끌면 예정이 바뀜, 390px 넘침 |
| 속도 | 현실 규모 + 배치 3개로 시나리오 3개 비교 |

## 7. 크기

엔진(배치 나누기 · 순서 · 결과) 하루, core 입력 · 판정 · 데이터 점검 반나절, 화면 4곳 하루, 시험 반나절 ~ 하루. **모두 3일 안팎.**

## 8. 정할 것

| 정할 것 | 추천 | 다른 안 |
|---|---|---|
| 1. 방식 | **B 배치를 배정 순서에 넣기** | A 계산 뒤 나누기(결과 그대로) · C B + 끄기 설정 |
| 2. 배치 밖 일의 순서 | **그 업데이트의 배치들 뒤** | 배치들 앞 · 리소스 순서대로 섞기 |
| 3. 물량 ≠ 배치 에셋 수 | **총량은 물량 기준, 넘치면 "물량 밖 n개"** | 에셋 수를 총량으로(물량 무시) |
| 4. 빠듯 기준 | **마감 전 "늦음 경고 영업일"(설정) 안** | 배치마다 따로 · 없음(마감 안 / 늦음만) |
| 5. 보여 줄 곳 | **업데이트 계획 · 에셋 배치 표 · 현황판 · 보고용 엑셀 · 데이터 점검** | 현황판 · 배치 표만 먼저 |
| 6. 바뀌는 결과 알림 | **처음 열 때 한 번 "배치가 있는 업데이트는 배치 순서로 계산합니다(완료 예정이 바뀔 수 있음)" 소식** | 알리지 않음 |
